## Question

`conf/postgres-init/01_schema.sql` defines a `pipeline_runs` table — `stage`, `category`,
`records_in`, `records_out`, `started_at`, `finished_at`, `notes` — with the comment "every
pipeline run records what it processed, so results are reproducible and we can show lineage
during the demo". Nothing writes to it `[observed: 0 rows, audit §2]`. Dead schema reads
worse on a CV than no schema, so either it gets a real job or it is dropped.

Decide:

1. **Keep or drop.** If kept, it is the project's lineage story: a grader asks "how do you
   know silver came from this bronze snapshot?" and the answer is a row. If dropped, the
   README stops mentioning lineage.
2. **What one row means.** Per stage, per run: which Iceberg snapshot id it read, which it
   wrote, counts in/out/rejected, wall-clock. Does the exactly-once gate write a row too?
3. **Who writes it.** Spark via JDBC at the end of each `foreachBatch` / job, or the driver
   script with `psycopg` after the job returns? The first is more honest about streaming;
   the second is simpler and cannot half-write.
4. **What the demo shows.** One query — `select stage, records_in, records_out, ... order by
   started_at` — as the "here is every run this data went through" move. Is that on the
   demo-moves list, and where?

The gate this feeds (`RR-13`): the silver reconciliation identity
`count(bronze) == count(silver) + count(rejects) + duplicates_removed` can be **read from
this table** rather than recomputed, which is what makes it a printable number.

Blocked on the silver decision, because silver is the first stage that has anything to
record.

## Resolution (closed 2026-09-07)

Grilled over three rounds; every item below was confirmed by Philip. Detail that is hard
to reverse is in [ADR-0008](../../../docs/adr/0008-run-ledger-as-lineage.md); terms in
`CONTEXT.md` *Lineage*.

### 1. Keep or drop — keep, as the **run ledger**

`pipeline_runs` is the ledger of every execution attempt of every **job** (an independently
rerunnable command). It is the lineage story: the answer to "how do you know silver came
from this bronze snapshot" is a row whose `inputs` names the snapshot, and whose `run_id`
is stamped on the snapshot silver wrote.

### 2. What one row means — schema

Typed core, JSON tail. `[decided]`

| column | type | notes |
|---|---|---|
| `run_id` | `UUID PK` | generated by the driver **before** execution; the canonical identity stamped into Iceberg snapshot summaries, ES documents (`source_run_id`), eval artefacts. Display label `silver · 2026-09-12 14:02 · 3f9a…`; order by `started_at`, never by id |
| `job_name` | `TEXT CHECK (job_name IN (…))` | vocabulary below; a test asserts the CHECK list equals the code registry |
| `spec_version` | `TEXT NOT NULL` | manually bumped per job (`SILVER_SPEC_VERSION` generalised); contracts are keyed `(job_name, spec_version)` so old rows stay valid |
| `status` | `running \| success \| failed` | success = execution completed with the **complete** output set validated; evaluation verdicts are never in this column |
| `category` | `TEXT NOT NULL` | `All_Beauty` |
| `data_scope` | `sample \| full` | sample and full never share a topic or a bronze table (`names_for` keys on topic) |
| `records_in / records_out / records_rejected` | `BIGINT` | meanings defined per job by its contract; null while `running` |
| `started_at / finished_at` | `TIMESTAMPTZ` | |
| `git_commit_sha`, `worktree_dirty`, `cleanliness_policy_version` | | captured at start; dirty = `git status --porcelain` non-empty over `src/ scripts/ conf/ tests/ pyproject.toml uv.lock Makefile run.sh docker-compose.yml`; `data/` excluded; notebooks included only if they execute transformations the published result uses |
| `inputs JSONB` | | name → concrete identity: table + snapshot id, `catalogue_load_id`, topic + offset ranges, source sha256, producer run ids |
| `outputs JSONB` | | name → concrete identity: **one entry per output table/artefact** (silver has three), model artefact paths, ES index names. Partial on `failed` |
| `counts JSONB` | | job-specific counts (silver's gate counts, bronze's `micro_batches`, `records_replayed`, per-producer counts) |
| `params JSONB` | | effective configuration the run used (regParam, thresholds, seed, executor config, frozen analytical parameters) |
| `notes` | `TEXT` | failure reason / named validation failure |

The existing `products` table gains `catalogue_load_id UUID` = the loader's `run_id` (ADR-0007).

**Job vocabulary (initial):** `produce · catalogue_load · bronze_drain · silver · gold ·
search_index_reviews · search_index_product_month · embeddings · theme_labels_llm ·
theme_classifier_train · theme_classifier_score · rag_answers`. Gates, evaluations, the
exactly-once proof, theme discovery and hand labelling are **not** runs: gates and
evaluations read the ledger and write JSON artefacts (RR-17); frozen assets carry their
own SHA and preparation spec in the runbook.

**Contract registry** (`src/common/runs.py`): per `(job_name, spec_version)` the required
`inputs`/`outputs`/`counts` keys and the count identity, returning **named** validation
failures. Job, inputs and params are validated before processing; outputs and counts before
`success`; `running`/`failed` rows may hold incomplete outputs. Silver, bronze,
`catalogue_load` and `produce` contracts are defined now; each later job registers its own
in its phase, and "contract registered" is a line in that phase's gate. Gold's structural
contract precedes the protocol freeze; the frozen analytical parameters go in `params`.

**Silver's identity** (from ADR-0007), read from the row:
`records_in == records_out + records_rejected + counts.collision_rows_removed`.

### 3. Who writes — driver-side psycopg, two writes, one row per attempt

Insert `running` before Spark starts (so the id exists to stamp on snapshots); finalize to
`success` only after every required output has committed and the contract validates.
Exceptions → `failed` with partial `outputs` preserved. A killed driver leaves `running`;
the two writes do **not** guarantee a `failed` row after every crash — the freshness gate
is what catches that. Never roll back automatically: it adds recovery complexity and could
undo another writer's commit; the repair is a rerun.

**Multi-output stages** (silver): each table commits atomically, the stage does not. A
successful row records the complete output set; downstream jobs **select all three
snapshots from one successful silver run and pin reads to them** — they never read "current"
silver. ADR-0007 amended accordingly.

**Bronze** (the streaming job), one row per driver invocation, native Iceberg sink kept:
- `records_in` = Σ input rows from a `StreamingQueryListener` accumulated for the whole
  execution (keyed by query id, run id, batch id) — **not** `recentProgress`, which is a
  bounded buffer. Missing accounting evidence fails validation.
- `records_out` = Σ `added-records` over snapshots whose summary carries this `run_id`;
  the snapshot id list is stored in `outputs`. Unchanged snapshot = zero output for this
  attempt, `snapshot_created=false`, still `success`.
- Replay: Iceberg 1.6.1's sink walks the current snapshot's ancestry for the latest epoch
  of the same query id and skips `epochId <= lastCommittedEpochId` `[observed: pinned
  Iceberg source, Philip]`. Identity is therefore
  `records_in == records_out + counts.records_replayed`, where replay evidence is matched
  by table + persistent query id + epoch on the current ancestry, the original epoch's
  committed count is checked against the replayed input count, and replayed snapshot ids
  are recorded separately from created ones. A non-empty batch with no attributed snapshot
  and no matching epoch → `failed`, reason `unattributed_batch`.
- Records both the persistent query id and the execution run id; `micro_batches` and
  offset spans go in `counts`/`inputs` as separate evidence; a checkpoint is exclusively
  owned by one execution.
- Two mandated tests, in an isolated fixture with no new Kafka records: (i) drain, delete
  the newest checkpoint commit for a **non-empty** batch, drain again → `records_replayed >
  0`, `records_out == 0`, table contents unchanged, `success`; (ii) missing attribution
  evidence is rejected.

**Producer** (`produce`): records `source_sha256`, `source_bytes`, `data_scope`, producer
config, `records_attempted`, `records_acked` (broker-acknowledged). Every Kafka record
carries header `producer_run_id`; bronze reads headers and stores the distinct producer ids
in `inputs.producer_run_ids[]` with per-producer processed / newly committed / replayed
counts derived from the data (the listener does not supply them).

### 4. Lineage gate and the demo move

`scripts/gate_lineage.py --mode development|publication [--category --scope]`. Reads the
expected chain from `conf/lineage_chain.toml` — edges reference **output names** (e.g.
`search_index_product_month ← gold.product_month`, `search_index_reviews ← silver.reviews`,
`silver ← bronze_drain.reviews_raw, catalogue_load.products`), each `required | conditional`,
with RR-12's cuts as `cut = true` + `cut_reason`. This is the **same file** RR-17's
`make eval-table` reads for declared cuts. A cut must not orphan a required dependent;
the gate validates the remaining required graph is complete.

Three printed blocks, then one line:
- **Provenance** — every success row's recorded inputs/outputs resolve (snapshots exist in
  the named table's history, stamped `run_id` matches, producer ids resolve to a source
  manifest; missing headers reported and fail publication).
- **Completeness** — for a fully drained, successful producer run: `records_acked` equals
  the distinct `(topic, partition, offset)` present in a pinned bronze snapshot.
- **Freshness** — the **published chain** (the selected, validated set of runs and exact
  outputs downstream consumes, not the newest row per job) is current: each edge's
  downstream input identity equals the upstream's recorded output, Iceberg current
  snapshot equals the recorded output, the ES alias's `source_gold_snapshot_id` equals the
  projection run's gold input (RR-01), silver's identity holds from the row.

Final line: `LINEAGE_GATE=PASS|FAIL gate_mode=… chain_clean=true|false
publication_ready=true|false chain_links_checked=N`. `chain_links_checked` counts edges
actually evaluated; `0` is FAIL. Required missing edges FAIL; explicitly cut capabilities
print `NOT_RUN`. Publication mode requires `chain_clean=true` and exits nonzero on failure;
development PASS may coexist with `publication_ready=false`. Nothing else in the verdict
vocabulary (no `PASS(dirty)`).

**Demo move — "every run this data went through"** (30–45 s, surface and position per
RR-11, suggested right after the silver gate): the ledger query
`select job_name, status, records_in, records_out, records_rejected, inputs, outputs,
started_at from pipeline_runs order by started_at`; take the silver row's bronze snapshot id;
in Spark SQL `SELECT count(*) FROM bronze.reviews_raw VERSION AS OF <id>` — equals
`records_in`. Then an earlier micro-batch snapshot of the full drain vs the completed drain
shows historical access. No `expire_snapshots` before submission; the sample is never
appended to the full table. This graduates the fog item *Iceberg time travel as a demo
move*.

### Schema change mechanics

`01_schema.sql` stays the fresh-install truth and inserts the baseline migration names and
checksums (generated from the files, never hand-maintained literals) into
`schema_migrations`. `conf/postgres-migrations/NNNN_*.sql` applied by `make pg-migrate`:
each file + ledger entry in one transaction, checksum recorded, changed applied files
detected, applied files skipped. No unconditional `DROP`: the migration asserts
`pipeline_runs` is empty and aborts otherwise. A test asserts fresh-init and
init+migrations agree on types, nullability, defaults, keys, CHECKs and indexes. Volume
reset is for intentional clean rebuilds only — it erases the ids that snapshots and ES
documents reference.
