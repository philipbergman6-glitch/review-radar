Trace one review from disk to the lakehouse

The skill: pick any single review and say, from memory, every station it passes through, what it looks like at each one, and why that station exists. This is the spine of the design doc and of the first minute of any Q&A answer.

Why this first

The brief says "the single most important factor is understanding" (brief, line 152). Everything downstream, silver, gold, Elasticsearch, the AI layer, hangs off the five stations that already run today. If you can narrate one review's journey without notes, the rest of the course has somewhere to attach.

The review we will follow

Line 1 of data/sample/All_Beauty.sample.jsonl is a real record. Its fields, per src/common/schemas.py:

{"rating": 5.0, "title": "…", "text": "…", "images": [], "asin": "B0…",
 "parent_asin": "B0…", "user_id": "AF…", "timestamp": 1588687728923,
 "helpful_vote": 0, "verified_purchase": true}

Nothing in the built pipeline ever parses this. It travels as a string until silver exists. Hold that thought; it is the answer to two quiz questions.

Five stations

1 · Replay producer built
Reads the JSONL line by line, sends each line untouched to Kafka. Key = parent_asin. acks=all, idempotent.
Why: the demo must not depend on a live API. A deterministic replay is still a genuine stream to everything downstream. Keying by product puts all of one product's reviews on one partition. src/ingest/producer.py docstring
↓ bytes + key
2 · Kafka topic reviews.raw built
Six partitions, single KRaft broker, 168 h retention. The review now has an address: (partition, offset).
Why: decouples ingest rate from processing rate, and lets Spark re-read from any offset after a crash. docker-compose.yml; deck 4
↓ readStream, micro-batches of ≤150,000 offsets
3 · Spark Structured Streaming, bronze job built
Selects value as payload string, plus key, topic, partition, offset, Kafka timestamp, and two wall-clock columns. Writes with outputMode("append") to the Iceberg table, checkpointing offsets per batch.
Why unparsed: "a transformation bug should never be able to destroy data." Why checkpoint: after a kill, resume from the last committed batch. src/spark/bronze.py lines 1–20, 160–175
↓ one Iceberg commit per micro-batch
4 · Iceberg table on MinIO built
lake.bronze.reviews_raw: Parquet files, zstd, partitioned by ingest_date, in bucket lakehouse. Each commit is a snapshot you can time-travel to.
Why Iceberg over plain Parquet: ACID commits, and the sink remembers the last committed batch id, which is the other half of exactly-once. Why MinIO: HDFS does not fit an 8 GB VM shared by four services. ensure_table(); docs/course-coverage.md §5
↓ "which metadata file is current?"
5 · Postgres as the Iceberg catalogue built
One row in iceberg_tables pointing at the table's current metadata JSON. Postgres does not hold review data.
Why: some single authority has to say which snapshot is the truth. Postgres will also play a second, separate role later as the product catalogue for the SQL join. README.md status table

The half that does not exist yet

From station 4 onward the map is design, not code: silver parses and dedupes, joins products from Postgres by JDBC, gold aggregates, Elasticsearch indexes enriched documents with an explicit mapping and a dense_vector, and the AI layer adds embeddings, LLM aspect sentiment, and RAG. Each gets its own lesson. The full table is in the architecture map.

2. Recall before you reveal

Why does bronze store the review as an unparsed string?
say it aloud, then click
So a parsing bug in silver can never destroy data. Bronze keeps the original bytes; silver can be re-run from bronze without going back to Kafka or the source file.
What two things together give exactly-once across a kill?
say it aloud, then click
Spark's checkpoint of the Kafka offsets per micro-batch, and the Iceberg sink recording the last committed batch id so a replayed batch is skipped, not appended twice.
What does Postgres do in the pipeline today, and what will it do later?
say it aloud, then click
Today: the Iceberg JDBC catalogue, one row per table pointing at the current metadata. Later: the product catalogue that silver joins by JDBC. Two roles, one database.
